# Congestion-window lab

Open the [lab](window-lab.html). Which window pairs do you expect to see at the first overload and in the next round? Run both rules from the same initial pair and compare those rows. Then reduce the buffer from 100 packets to 20. Predict how that changes the number of rounds with an idle link. Compare after running.

The model keeps one path with an empty-queue bandwidth-delay product of 100 packets. It assumes saturated senders, identical feedback timing, and simultaneous reactions. A round records the current windows before either sender updates. The queue is estimated as the window sum minus the bandwidth-delay product, bounded by zero and the buffer's capacity. Link use is the window sum divided by the bandwidth-delay product, capped at 100 percent. The overload signal turns on only when the total exceeds the pipe plus buffer. This gives a model of window dynamics. It has no events for individual transmissions, acknowledgments, or retransmissions, and each round counts once even if the round-trip time differs because of queuing.

To test a new design, use a copy of `window-model.js`. Ask an LLM to implement a rule that accepts its current window and the shared overload signal. Keep the rule's assumptions in the open. Try replacing only the AIMD reduction factor and compare with the original by sweeping the buffer from 0 to 200. Record the rounds with overload, the rounds below full use, and the change in the gap across consecutive congestion events. What benefit can your rule deliver, and on which workloads does it give that benefit up? Include at least one workload that starts the two flows far apart and one in which both start with the same window.
